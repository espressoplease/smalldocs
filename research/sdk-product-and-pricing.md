# Turning the SmallDocs renderer into a developer product

Research checked against official vendor documentation on 24 August 2026.

## Recommendation in one page

SmallDocs should present the renderer as a small developer product:

> Render agent-written Markdown as a complete SmallDocs reading surface inside
> your application.

The first public documentation should lead with one working result:

```html
<div id="report"></div>

<script type="module">
  import { render } from "https://smalldocs.org/sdk/v1/smalldocs.js";

  const markdown = "# Research report\n\nGenerated by your agent.";
  const view = await render("#report", markdown, {
    publishableKey: "sd_pk_test_..."
  });
</script>
```

The developer supplies finished Markdown. SmallDocs discovers and renders the
features in that document. The developer does not parse fences, list required
features, or write a renderer pipeline.

The initial commercial model should be:

- All rendering capabilities on every plan.
- A permanent development and low-volume free tier.
- Paid usage based on successful renderer starts, not document size, tokens,
  features, seats, or calls to `view.update()`.
- One publishable browser key per environment, restricted by allowed origins.
- A small paid plan with included usage and optional overage.
- Custom pricing only for volume, support, private distribution, or contractual
  requirements.

Do not launch paid billing at the same time as the first external technical
preview. First put the SDK in two or three real applications, measure loads and
asset costs, and confirm that developers understand the integration and billing
unit.

## What good SDK documentation actually contains

### 1. A result before a taxonomy

The first page should answer four questions without requiring navigation:

1. What will appear in my application?
2. What code do I paste?
3. What input do I provide?
4. How do I know it worked?

Stripe starts from jobs such as accepting a payment or selling a subscription.
Resend starts from sending one email. Mapbox starts from displaying one map.
SmallDocs should start from displaying one agent-generated report.

The first example should not begin with agent orchestration. Begin with a
Markdown string so the product boundary is visible. Put agent recipes on the
next page.

### 2. Progressive disclosure

Keep these documentation layers separate:

- Quickstart: one file, one mount element, one render call.
- Concepts: Markdown input, rich fences, isolation, caching, and lifecycle.
- Guides: agents, React, Vue, navigation, styling, CSP, performance, and errors.
- API reference: `render`, `update`, `destroy`, options, return values, and
  stable error codes.
- Operations: test and live projects, allowed origins, usage, versions,
  migration, status, and support.

Resend is particularly good at this. Its main quickstart is install, set the
key, send. The many framework examples exist nearby but do not make the basic
path harder.

### 3. Plain JavaScript first

Document the browser module before framework wrappers:

```js
const view = await render("#report", markdown, { publishableKey });
await view.update(nextMarkdown);
view.destroy();
```

Then provide React, Vue, Svelte, and Next.js recipes that call the same core.
This prevents the framework packages from becoming separate products with
different behavior.

Mapbox, Clerk, Liveblocks, Resend, and Nutrient all provide framework-specific
paths, but their underlying product concepts remain recognizable.

### 4. A real isolated example

Every release should be packed or served, then consumed from a clean example
application that does not import repository globals. The example should be
deployable and linked from the docs.

The current cross-origin SDK test is the correct foundation. Turn its customer
fixture into a public `examples/plain-html` project once the API reaches v1.

### 5. Test and production environments

Create separate publishable keys:

- `sd_pk_test_...` works on localhost and preview domains, is not billable, and
  is visibly labelled as test use in the dashboard.
- `sd_pk_live_...` works only on configured production origins and is metered.

Stripe makes this separation central to its integration. Clerk and Liveblocks
also use browser-safe project keys. A browser publishable key is an identifier,
not a secret. Documentation must say that directly.

### 6. A visible security and data-flow explanation

The security page should show the mechanism:

```text
Host application
  -> downloads versioned SmallDocs code
  -> sends Markdown to the isolated renderer in the browser
  -> receives resize and lifecycle messages

SmallDocs service
  -> serves code and the renderer shell
  -> records project, allowed origin, SDK version, and one usage event
  -> does not receive the Markdown in an HTTP request
```

Also disclose the important caveat: hosted JavaScript executes in the user's
browser and can read the document it renders. A compromise of that hosted code
could expose plaintext. Remote content such as videos, links, and any future
image behavior needs a separate network policy.

Document:

- iframe sandbox behavior and origin validation
- sanitizer contract
- host CSP requirements
- supported browsers
- accessibility expectations
- remote dependency and content requests
- retention for usage metadata
- incident and version support policy

### 7. Exact versioning

Use both a stable major URL and immutable exact releases:

```text
https://smalldocs.org/sdk/v1/smalldocs.js
https://smalldocs.org/sdk/1.0.3/smalldocs.js
```

`v1` may advance only within documented backwards-compatible v1 releases. The
exact URL never changes. npm packages use semantic versioning. Publish a
changelog and migration guide before the first breaking release.

Stripe documents the relationship between API and SDK versions in detail.
SmallDocs needs a smaller version of that promise, not an unversioned latest
script.

### 8. Billing documentation before billing code

Publish the exact answer to each of these before charging:

- What counts as a renderer load?
- Do failed renders count?
- Do `update()` calls count?
- Do several documents on one page count separately?
- Does local development count?
- When does usage reset?
- What happens at the free limit?
- Is overage automatic or opt-in?
- Where can a customer see current and projected usage?

Mapbox and TinyMCE both define initialization-based units with examples.
Resend and Liveblocks expose current usage, limits, alerts, and overage rules.
That clarity matters more than the exact price.

### 9. Documentation for agents

Resend publishes an `llms.txt` index and full Markdown documentation. Stripe
now exposes docs through its CLI and provides agent setup. SmallDocs already
has an agent skill, so the developer product should add:

- `/developers/llms.txt`
- Markdown versions of every guide
- a short integration skill or recipe
- copyable prompts that reference the stable docs rather than duplicating them
- an evaluation fixture that checks whether agents produce the correct
  integration without inventing feature declarations

The human quickstart remains primary. Agent material should make the same
contract easier to discover, not introduce another contract.

## The SmallDocs developer product

### Product surface

Add a Developers entry to the public site with this structure:

```text
/developers
  Overview and live example
  Quickstart
  Guides
    Agent-generated documents
    Update and destroy
    Styling and themes
    Navigation and collapsible sections
    Content features
    React and other frameworks
    Security and privacy
    CSP and deployment
    Performance and caching
    Troubleshooting
  API reference
  Examples
  Pricing and usage
  Changelog
  Status
```

The existing `/docs` route is the SmallDocs reader, so do not overload it.
Use `/developers` now. A dedicated developer subdomain can follow if the docs
outgrow the main application.

### Account and project surface

Reuse the existing SmallDocs account and Stripe billing foundation, but model
the SDK as a separate product from Cloud. Resend explicitly favors separate
subscriptions for distinct products rather than one plan that obscures what a
customer is buying.

Each developer account needs:

- Projects
- Test and live environments
- Publishable key creation and rotation
- Allowed origins
- Current SDK version
- Daily and monthly renderer loads
- Free allowance, projected usage, and alerts
- Billing plan and overage preference
- A copied integration snippet already populated with the project key

Do not require a secret key for a browser-only renderer. If a server API is
added later, give it a separate restricted secret key and separate docs.

### SDK API evolution

Preserve the call already built and add one optional configuration object:

```js
const view = await render("#report", markdown, {
  publishableKey: "sd_pk_live_..."
});
```

Keyless rendering can remain available on localhost during the preview. A live
key is required on production origins once metering begins.

The server already receives an embed request containing the parent origin. The
next commercial slice can add a publishable key, validate it against that
origin, and record one content-free usage event after the first document has
rendered. Markdown continues to travel only through browser `postMessage`.

### Definition of one renderer load

Recommended definition:

> One renderer load is counted when a new SmallDocs view successfully renders
> its first document. Updating that same view, opening sections, interacting
> with cells, or presenting slides does not count again. Creating another view
> counts as another load. Test keys and localhost do not count.

This matches the object a developer creates and the value their user receives.
It also works with the current SDK lifecycle.

Do not charge by:

- Markdown bytes, because it encourages awkward document splitting.
- tokens, because SmallDocs does not perform inference.
- rich feature type, because it undermines portable agent output.
- end-user seats, because anonymous reading would require new identity data.
- every `update()`, because agents may stream or revise one result several
  times in a single surface.

## Pricing hypothesis for a private beta

These numbers are a testable starting point, not a final price list.

### Development

- £0
- Unlimited test-mode use on localhost and preview origins
- 25,000 live renderer loads per month
- One live project
- Three allowed production origins
- Full document rendering
- Community support
- Optional SmallDocs attribution as a growth mechanism

### Pro

- £29 per month
- 250,000 live renderer loads per month
- Five live projects
- More allowed origins
- Remove attribution
- Email support
- Usage alerts
- Opt-in overage, initially tested at £1 per additional 1,000 loads

### Scale

- Contact SmallDocs
- Higher committed volume and volume discounts
- Contractual support or uptime requirements
- Private or self-hosted distribution where appropriate
- Security review, DPA, and procurement support

Why start here:

- Resend establishes a $20 developer entry plan with meaningful included use.
- Liveblocks starts paid use at $30 per month.
- Mapbox gives a broad free load allowance and then charges per 1,000.
- TinyMCE charges much more because its surface is a production editor with
  premium authoring features.
- SmallDocs rendering is client-side and should be easier to adopt than an
  editing or collaboration system.

Keep overage off by default during beta. Notify at 50, 80, and 100 percent.
Give a grace period rather than suddenly blanking documents in a customer's
production application. The dashboard should show the precise events behind a
usage total without storing document content.

### What plans should not gate

Do not divide plans into Markdown, charts, sheets, and slides. The differentiator
is that agent output stays portable and can use the full SmallDocs language.
Every plan should render every supported document feature.

Plans can differ by:

- volume
- origins and projects
- branding
- support
- usage retention
- uptime commitments
- private distribution
- security and procurement terms

## Delivery sequence

### Loop 1: technical preview

Already substantially present:

- versioned browser module
- isolated iframe renderer
- `render`, `update`, and `destroy`
- a real cross-origin customer fixture
- browser and HTTP tests

Complete the non-image feature parity and network measurement before inviting
external developers.

### Loop 2: documentation preview

Build `/developers` with:

- live editable Markdown demo
- plain HTML quickstart
- agent-output recipe
- lifecycle guide
- security and architecture page
- feature compatibility matrix
- browser and CSP page
- exact version and support statement
- public example repository

Ask three developers to integrate without assistance. Record where they stop,
what they search for, and what code they invent.

### Loop 3: project identity

Add:

- developer projects under the existing account
- test and live publishable keys
- allowed origins
- key rotation
- project-populated quickstart snippets
- usage events with no Markdown or document identifiers

Keep the product free during this loop. Validate counting against application
logs and ask pilot customers whether the unit matches their mental model.

### Loop 4: usage visibility

Add:

- daily and monthly usage charts
- clear load definitions and examples
- alert thresholds
- projected month-end usage
- exportable usage records
- a visible distinction between test and live traffic

Do not add billing until customers can independently reconcile the number.

### Loop 5: paid beta

Create a separate Stripe product from SmallDocs Cloud:

- Development
- Pro monthly
- opt-in overage
- Scale contact path

Add terms for the hosted SDK, attribution, allowed use, version support, and
usage measurement. Have counsel review how these terms interact with the
repository's Elastic License 2.0 before public sale.

### Loop 6: native lazy renderer

Continue the existing parity program. Replace the iframe engine only when the
native renderer matches the published compatibility matrix. The public API,
keys, docs, projects, and billing unit remain the same.

## Decisions to make before paid launch

1. Is free-plan attribution worth the visual cost inside customer documents?
2. Should production overage pause, continue with grace, or require explicit
   opt-in?
3. What usage retention does the dashboard need?
4. Does Scale include a self-hosted commercial SDK, a private CDN package, or
   only contractual hosted service?
5. Are forms part of rendering or a later interactive product?
6. Which remote content types are supported, proxied, or refused?
7. What performance budget must the full-fidelity iframe meet before preview?

Images are intentionally not part of this commercial plan yet. Existing
Markdown image behavior should not turn into an upload, proxy, or hosting
service without a separate product and security decision.

## Immediate next artifact

Build the documentation preview before the billing system. A developer landing
page and working quickstart will reveal whether the product boundary is clear.
The first preview should let someone paste Markdown, see the full renderer, copy
the exact integration, and inspect the network behavior without creating an
account.
